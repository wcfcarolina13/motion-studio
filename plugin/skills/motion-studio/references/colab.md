# Colab rules: every job, every stream

Colab runtimes drop without warning, GPUs are refused for hours, and units burn while a runtime is held. These rules make a run lose at most the file in progress and never burn units unattended. `assets/colab/cli/run_colab.sh` follows them by default; a new remote job should run through it (swap `SETUP=` and `RENDER=`) rather than a script of its own. A fuller rulebook with sources is kept on the owner's machine; this page is the part the engine enforces.

## Outputs survive a dropped session

- **Whole files only.** A remote script writes each output somewhere else (`/content/tmp`), then `os.replace()`s it into `/content/out`, and lists it in `/content/out/MANIFEST.tsv` (name, size, sha256). `publish()` in `remote_render.py` does all three; copy it. `colab ls` gives no size or date, so a file written in place could be pulled half-written.
- **Pulled as they finish.** `pull_live.sh` starts before setup and lists `/content/out` every 30 s (the listing goes through the contents API, so it answers while the kernel is busy). Each new file is downloaded beside its target, checked against the manifest, and renamed into place only when it matches; a failed or mismatched download is deleted and tried again next pass. On 2026-11-24 a run lost 64 of 76 finished stills because downloads were left until the end.
- **Done marker last.** The remote script writes `/content/out/RENDER_DONE` after its last output (and prints `RENDER DONE`). The puller stops after one more pass once it sees it.
- **Resume, don't redo.** `retry_colab.sh` sends only the jobs in `jobs.json` that have no output yet (a non-empty `<id>.*` in the output folder), so a rerun after any failure pays only for what is missing. A remote script also skips an output that already exists.
- **Belt and braces.** At the end, anything the render named (`OUTFILE <name>`) that is still missing is fetched once more, with the same check. Anything still missing is listed as `MISSING` and the run exits 2.

## A run never burns units unattended

- **The CLI's request timeout is raised to 60 s.** google-colab-cli waits 10 s for each request by default, but a cold kernel takes 12 to 39 s to answer, so the first calls after "Session READY" died with "Connection was lost" (CLI issues #285 and #264, confirmed against the installed CLI's client.py, which reads `COLAB_CLI_REQUEST_TIMEOUT`). This explains most dropped smoke tests and the setups that never started on 2026-11-25. That variable covers only the CLI's Colab API calls. Kernel calls (exec, file reads) go through jupyter_kernel_client, which reads its own `REQUEST_TIMEOUT` (default 10 s in the CLI installed on the Mac, 30 s in jupyter-kernel-client 1.0.4). The first real run after #124 still died with "ReadTimeout ... 8080-gpu-l4-... (read timeout=10)". `run_colab.sh` and `pull_live.sh` export both `COLAB_CLI_REQUEST_TIMEOUT=60` and `REQUEST_TIMEOUT=60` unless they are already set. The CLI's 120 s allocation timeout is also behind the orphan "[?]" runtimes (#263); the reaping in run_colab.sh still covers those. `colab exec` exits 0 when the remote code fails, so the runner keeps reading markers and files, never the exit code alone. Trade-off: a dead runtime now takes up to 60 s per call to notice instead of 10, within the runner's own `timeout` limits.
- **Every call has a local time limit** (`timeout`), because a dropped connection can leave a CLI call waiting forever. The render exec has no remote time limit (`--timeout 0`, which is an idle limit, not a total), and the stall watch takes its place.
- **Stall watch.** Activity is a line of render output or a new file pulled. After `STALL_ALERT` seconds without either (default 900) the run alerts; after `STALL_STOP` (default 1800) it gives the render up, makes the last pull and stops the session. Render scripts print progress at least every few minutes (Wan prints every step). No heartbeat thread: it would keep the watch quiet while the GPU hangs.
- **Setup runs detached.** The setup script is uploaded to `/content/setup.py` (checked by size on the runtime), and a short exec starts it as its own process with output to `/content/setup.log` and its exit code to `/content/setup_rc`, then returns at once. Short probes every 15 s stream the log into `setup.out` and read the exit code. This replaced running setup inside one long `colab exec`. That exec could drop right after "PHASE setup" and leave no setup at all: no `setup_alive` three times on 2026-11-25, each with a custom setup that ran a pip upgrade and a 20-40 GB download. Or it could hang while the card billed: 19 min on an L4, 2026-11-25. The start exec is idempotent: it never starts a second copy while one runs or after one finished, so a start that dropped after starting is just sent again. With no confirmed start in `SETUP_SEEN` seconds (180) the run exits 4, which retry_colab.sh retries at once. `SETUP_PROBE_FAILS` (8) probes missed in a row means the runtime stopped answering, also exit 4. A setup that exits non-zero, or whose process dies without an exit code (killed, usually out of memory), fails the run at once with the end of its log, exit 1. Before, the render waited 45 min for a setup that had already crashed. No log output and no `setup_alive` touch for `SETUP_WAIT` (2700 s) is a stuck setup, exit 1. Setup scripts need no change. They still run start to finish in one Python process and hand over through files (`paths.txt`, `model_path.txt`), and `setup_alive` still counts as a sign of life. Trade-offs: the setup no longer runs in the render's kernel, so a setup that left Python objects for the render would break (none of ours do; hand over through files); and a probe every 15 s is about 4 short execs a minute during setup.
- **The render runs detached too** (2026-11-25). Inside one long `colab exec`, the exec's websocket dropped ("RuntimeError: Connection was lost", colab_cli runtime.py) on every render over a minute or two that day, and the render died with it (Krea 2 loaded in 26 s, dropped at 194 s, 0 files). `run_colab.sh` now uploads the render script as `/content/render.py` and starts it as its own `python -u` process (pid, `render.log`, exit code in `render_rc`), the same way as setup. A probe every `RENDER_POLL` s (15) copies the log into `render.out` whole and in order (whole lines, up to 64 KB a probe), so OUTFILE lines and tracebacks are kept. The run ends on the exit code: code 137 means the process was killed, most often out of memory. `RENDER_PROBE_FAILS` (40, about 10 min) missed probes in a row means the runtime is gone. The puller, the manifest checks, the stall watch and the unit budget are unchanged, and render scripts need no change. Trade-off: the log arrives in 15 s steps instead of live.
- **A pipeline class the weights name must load.** `remote_stills_setup.py` reads `model_index.json`'s `_class_name` after the download. If diffusers lacks that class, setup tries a source install once, then stops with a clear message, instead of the render failing after the download (MOSS-Image: "module diffusers has no attribute MOSSImagePipeline"; diffusers 0.43.0, the latest release, has none). A model whose card ships its own pipeline code sets `"custom_pipeline"` or `"trust_remote_code"` in stills_models.json, and the render passes them to `from_pretrained`. Root `*.py` files now download with the weights for that case.
- **One runtime per batch, whatever the mix.** Setup (pip install and model download) costs about 15 minutes per runtime against a few minutes of rendering, so put every shot that uses the same model in one jobs.json, even when shots differ in style. Each job may carry its own `"style"` (day, night, diagram), and render scripts use `job.get("style", batch_style)`. Split a batch only into lanes, never by style.
- **Stills route.** Owner's rule (2026-11-25): step-distilled "turbo" stills are out for anything that ships ("we definitely can't use those weak models"). They are for drafts and layout only. `python3 assets/colab/cli/shots_to_jobs.py shots.json <in_dir> [--model NAME]` turns `{"style", "model"?, "settings"?, "negative"?, "shots": [{"id", "prompt", "style"?}]}` into one job per take (seeds 7 and 19, named `<id>_s7.png` and `<id>_s19.png`), so a retry resends only the missing takes. It also writes `model.json`, the model from `assets/colab/cli/stills_models.json` with any `"settings"` overrides of its pipeline call, and `min_vram_gb`. Then run `SETUP=remote_stills_setup.py RENDER=remote_stills_render.py run_lanes.sh <in_dir> <out_dir>`. The models are:
  - `z-image`: full Z-Image, 40 steps, CFG 4, 1344x768, 20 GB or more, so L4 or A100.
  - `qwen-image-2512`: Qwen-Image 2512, 40 steps, true CFG 4, 1664x928. A100 only for now (`min_vram_gb` 40 sends the run to an A100): whole on the card at 70 GB or more (`full_gpu_gb`), sequential offload below that.
  - `z-image-turbo`: 9 steps, no guidance. Draft only; it needs `--draft`.
  - `moss-image-sft`: MOSS-Image-SFT (5B, Apache-2.0), 50 steps, CFG 3, empty negative, 1344x768, diffusers 0.38 or later; L4 with model offload, whole on the card from 40 GB. Settings are the model card's, not yet measured here.
  - `chatgpt-image-codex`: ChatGPT images through the Codex CLI on the Mac, not Colab (below).

  - **Bake-off, 2026-11-25** (on an L4, since no A100 was free): ChatGPT images via `codex exec` won clearly. It drew 9 stills in about 6 minutes with right anatomy and scale, dark night skies and no garbled text. Full Z-Image took 155 to 215 s a still and still got object structure wrong (a seat on a pedestal, a drawn border, a melted hand truck). Qwen-Image 2512 ran out of memory on the L4 under model offload, because that moves its whole 40 GB transformer onto the card; it is marked `"offload": "sequential"` (one layer at a time) and a sequential retry was running.
  - **Codex route.** `python3 scripts/codex_stills.py shots.json <out_dir> --allow-codex` runs one `codex exec` per shot, one at a time, in a fresh folder. It takes the newest PNG written during that call (in the folder or under `~/.codex/generated_images`), re-rolls up to `--tries` (3) when the picture isn't landscape between 1.4:1 and 1.85:1 or a faceless shot shows a face, keeps the untouched original in `originals/` and writes the working copy centre-cropped to 16:9 with PNG text `motion-studio-model: chatgpt-image via codex`. A rerun redoes only missing shots. `usage.log` counts Codex calls; `review.tsv` lists shots that ran out of tries or got an unclear face verdict. `CODEX_CMD`, `CODEX_ARGS` (default `-m gpt-6-luna -c model_reasoning_effort="low"`), `CODEX_IMAGES` and `FACE_CHECK_CMD` (`{path}`; `off` skips) override the parts.
    - **The default for finished stills** (owner, 2026-11-25: "Chatgpt makes the best images by far and it's obvious", then "Yeah let's do it" to redrawing every Survive Year 1 still). The open-model route on Colab is the fallback when the Codex allowance runs short or Codex is down. An episode's roughly 120 images use about 10 to 15% of a week's allowance, so check `usage.log` against what is left before a full redraw. The script still refuses without `--allow-codex`, so a run spends only when asked. First real run: 4 shots in 4 calls, no re-rolls, anatomy right on all four.
    - **Scale.** Give shots.json the film's `"sizes"` (or pass `--sizes script.json`) and name each shot's `char_in_frame` and `props`. Those shots get scalecheck's scale sentence plus "keep these proportions exactly", and after the run they go on the marking page `<out>/scale/index.html` (listed in review.tsv). Mark it, download marks.json, run `python3 scripts/scalecheck.py check <out>/scale-list.json marks.json`, delete a failing still and re-roll it with `--only <id>`. The marks are needed because the prompt alone fell short: a booth asked for at 1.3 times the man's height came out about 1.1 times. A size sheet with a missing entry or source stops the run before any Codex call. In a film the render gate checks the stills again on their panels.
    - Trade-offs:
      - Each re-roll is another Codex call. Three tries per shot caps the cost at three times the shot count.
      - The face check asks the Claude CLI to look at each faceless still (the owner's Claude plan, about a minute a still at most). A vision judge reads ink-and-gouache faces better than a classic face detector would, but it can be wrong either way; an answer that is neither FACE nor NOFACE keeps the still and lists it for a person.
      - The 16:9 crop re-encodes the pixels, so the working copy loses OpenAI's C2PA provenance manifest. The original keeps it, and the copy names its original. A rendered video never carries a still's C2PA data anyway, since every frame is drawn anew; that is ordinary rendering, not stripping to hide anything (publish.md, D1_provenance_kept), and the untouched originals stay on file.
      - The crop takes about 1/16 off the top and bottom of a 3:2 picture, so prompts should keep the subject away from those edges.
      - The CLI flags that turn the image tool on are the Mac's to confirm; `CODEX_ARGS` carries whatever the bake-off used.

  The default stays `z-image` until the owner says yes to the Codex route or Qwen's sequential-offload retry proves out (bake-off below). The pipeline is loaded with `DiffusionPipeline`, which reads its class from the model's own `model_index.json`, so a new model is a new entry in the file, not new code. Every still carries PNG text `motion-studio-model`, and a draft model's stills also carry `motion-studio-draft`. `check` flags draft stills and `render` refuses them, reading the source of an upscaled copy, since Real-ESRGAN drops the text.
  - Trade-offs:
    - Full models take about 40 steps against Turbo's 9, so a still takes roughly four times as long (not yet measured here).
    - Qwen-Image needs an A100, at about five times an L4's units, and below 70 GB (`full_gpu_gb`, the bake-off's threshold) it loads one component at a time (slower, same pictures), so a 40 GB A100 runs it offloaded.
    - Licences, from each model card's `cardData.license` (2026-11-25): Qwen-Image 2512 and full Z-Image (`Tongyi-MAI/Z-Image`) Apache-2.0, HiDream-I1-Full MIT. FLUX.2-dev is non-commercial and excluded.
  - Card sizes: a T4 (14.6 GB) ran out of memory on Z-Image's first still (2026-11-25). The render refuses a card under the model's need before loading weights. Any setup script can declare `MIN_VRAM_GB: <n>`; over 16 keeps it off the T4, over 24 puts it on an A100.
- **A dead render is caught.** A crash inside the kernel prints IPython's traceback, whose first line doesn't start with "Traceback", so the runner matches "Traceback" or "FAILED" anywhere in the render output. When the exec returns early with neither, the run waits on the puller as before. It also probes the kernel about every 5 minutes: if a one-line exec answers at once and there is no RENDER_DONE, the render is dead, and the run stops with exit 2. A T4 out-of-memory crash once sat "detached" for 10 minutes while billing (2026-11-25).
- **Exec returned early.** "Connection was lost" does not stop the kernel. Unless the output shows a crash, the run keeps the session and keeps pulling under the same stall watch until `RENDER_DONE`. Never resubmit a render after a lost connection without checking what the runtime already made: the first one may still be running.
- **Alerts.** `COLAB_ALERT` names a command run with the message (a desktop notification, a message to a thread). Unset, alerts go to the console and `usage.log` only.
- **Unit budget.** The balance is logged at the start and end of every run (`usage.log`), with the units spent. During the render it is read every 5 min; past `UNIT_BUDGET` units for the run (default 20) the render is given up. The balance moves in steps, so this is a backstop. Top-ups need the owner's word with the cost first.
- **Teardown.** The session is stopped on every exit path, by name (`colab stop -s <name>`), never all sessions: another stream may be running one. Every run gets its own name: the default is `ms-<out dir>-<pid>`, and a run refuses to start (exit 2) when `colab sessions` already lists its name. Two runs that shared a name on 2026-11-24 left the first run's runtime unnamed ("[?]"), so the CLI could neither pull from it nor stop it, and 14 finished stills were stranded. A file lock around `colab new` would not help, because the clash is between the runs' names, not their timing. An unnamed runtime is stopped by hand in Colab's Manage sessions. A lane's name is `ms-<out dir>-lane-<k>-<pid>` (its folder is `<out>/.lane-<k>`).
- **Cancelling a run mid-request.** Stopping a run (kill, `longjob stop`) while `colab new` is still out used to leave a runtime billing: the stop found no session, then the runtime came up a moment later with nothing behind it (2026-11-25, about 35 min of L4, and the next lane looped on "cards busy"). Now the run's cleanup kills the request and watches `colab sessions` for its own name for `NEW_GRACE` seconds (150), stopping it when it appears. A run killed with SIGKILL gets no cleanup, so the next check below is the backstop.
- **Orphans holding a card.** When a card answers "precondition failed", the run first stops our own orphans: runtimes named `ms-…-<pid>` whose pid is no longer a live `run_colab.sh` on this machine. It alerts with each name it stopped and asks for the card once more. Runs with a custom `COLAB_SESSION`, other projects' runtimes and live lanes are left alone. Trade-off: this tells an orphan by its pid on this machine, so a run of ours started from another machine would look orphaned; only the Mac runs Colab jobs today.
- **Fix runtime problems without asking** (owner's standing permission, 2026-11-24, for every session and agent). Stuck, stalled, orphaned or unnamed ("[?]") runtimes that our runs started are fixed on the spot: stop them with `colab stop -s`, or in Colab's Manage sessions in the owner's browser when the CLI can't reach them, then rerun only the missing jobs. Afterwards, tell the owner in one line what was stopped and why. The limits:
  - Touch only runtimes our pipeline started. That means a name from `run_colab.sh` (`ms-…` or the run's `COLAB_SESSION`), or an unnamed runtime whose GPU and start time match one of our runs. The same account runs other projects' sessions, so leave any runtime you can't tie to our runs alone and tell the owner about it.
  - The permission covers stopping and rerunning. It does not cover buying compute units or upgrading the plan, which still need the owner's word with the cost.
- **Hidden runtimes.** A failed `colab new` can leave a runtime assigned and billing with no local name (`[?]` in `colab sessions`). The run checks after each failed request and alerts; it can't stop one by name, so stop it in Colab's Manage sessions.

## Getting a GPU

- `COLAB_GPUS` sets the order. By default a run asks for the cheapest GPU that fits: `L4` for the Wan scripts, and `L4 T4` for any swapped-in job (stills, voice). An A100 burns about 11 units an hour against about 2.3 for an L4 (2026-11-24), so it is used only when asked for (`COLAB_GPUS="A100 L4"`). The trade-off: Wan on an L4 runs 4-bit with the Lightning LoRAs at 720p, where an A100 runs 8-bit, so a hero clip that needs the best quality asks for the A100. G4 is never offered to the CLI. T4 (16 GB, no bf16) can't hold Wan 14B. Since about 2026-11-23 the CLI often answers 503 for A100 and L4; `retry_colab.sh` waits that out (every 20 min, 9 tries). A runtime started in the browser can't take over: google-colab-cli 0.8.0 has no attach or connect command (`colab url` only goes the other way, and `colab new` can't take an existing runtime), so there is no browser fallback for a 503 until a newer CLI adds attach (checked 2026-11-25).
- **Two lanes by default for big batches, one card type each.** The owner's plan holds about one runtime per GPU type: L4+T4 and A100+L4 ran together on 2026-11-24, but a second L4 was refused ("precondition failed") while one was active, twice. `run_lanes.sh <in_dir> [out_dir] [lanes]` deals the jobs round-robin and gives lane k the k-th card of the order. For stills and voice the default is lane 1 on L4 and lane 2 on T4. A Wan batch runs as one lane on L4 unless `COLAB_GPUS_2` names another card, and an A100 costs about five times an L4. Each lane is its own `retry_colab.sh` run with its own session name and its own `out_dir/.lane-<k>`, and finished files move into out_dir. Run voice on the T4 lane, and keep Mac work (maps, upscales, grading, assembly) going alongside instead of waiting on Colab. A "precondition failed" on every card means the account's runtime of that type is in use (another lane or another project): `run_colab.sh` exits 3, and `retry_colab.sh` waits 5 minutes without using a try, for up to 6 hours (`BUSY_MAX`). Trade-offs: two runtimes burn units faster for less wall time; a single lane keeps its full fallback order (L4, then T4), while each of two lanes has one card, so a lane waits rather than falls back.
- **Smoke test before uploading anything:** `nvidia-smi`, a tiny CUDA operation and free disk, logged with `colab version` and `colab usage`. A runtime that fails it is treated like no GPU (exit 1, retried).

## Models

- Models download on the runtime, never through the Mac. Setup retries each download with backoff and keeps finished files in the runtime's cache; a new runtime downloads again. Hugging Face's Xet CDN is off (`HF_HUB_DISABLE_XET=1`) after a 429 killed a run. With a read-only Hugging Face token (owner OK'd 2026-11-24), run_colab.sh uploads it from `HF_TOKEN_FILE` (default `~/.config/motion-studio/hf_read_token`, mode 600 on the Mac) to `/content/.hf_token`, and setup turns Xet back on with `HF_XET_HIGH_PERFORMANCE=1`; after two failed tries it falls back to plain HTTP. No token file means anonymous downloads with Xet off. The token must be read-only (fine-grained, no write scope), is never printed, and never goes in chat, memory, logs or the repo. Trade-off: it sits on the runtime's disk until the runtime stops, so a shared or leaked notebook could expose it; read-only scope limits that to downloading public and gated models as the owner.

## Drive (opt-in, attended runs only)

`COLAB_DRIVE_DIR=<folder under My Drive>` adds a second copy: `remote_drive.py` mounts Drive and a thread in the kernel copies each whole file there (temporary name, then rename, checked against the manifest), `RENDER_DONE` last; the run gives it up to 5 min to catch up before stopping. The Mac puller stays the main copy because mounting Drive asks for a consent click in a browser on each new runtime and grants the whole Drive, so an unattended run would sit at the prompt. If the mount fails, the run alerts and carries on with the puller. The Drive layer is untested on a real runtime as of 2026-11-24.

## Content

- Colab forbids deepfakes. Any lip-sync, face-swap or voice job that involves a real person's face or voice is checked with the owner first, and never runs on Colab without that. Original characters are fine.
- The account holder accepts Colab's terms and signs the CLI in themselves (see longform.md).

**Anatomy gate on pulled stills.** After a stills run, on the Mac: `python3 scripts/anatomy.py <out_dir> --jobs <in_dir>/jobs.json --fix`. It judges each new still with people (anatomy.py, picture-truth.md rule 12), logs verdicts to `judge.tsv`, deletes a failed still and moves its seed by 1000 in jobs.json, so rerunning `run_colab.sh` (which redoes only missing stills) draws just those again. After `--tries` (3) fails a still is kept and listed in review.tsv. Exit 1 means something was redrawn or needs a look.
